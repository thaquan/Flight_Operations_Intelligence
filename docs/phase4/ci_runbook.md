# CI and recovery runbook

## What runs on GitHub Actions

The workflow `.github/workflows/ci.yml` runs on pushes to `main`, pull requests and manual dispatch. It uses Python 3.13 and an ephemeral PostgreSQL 17 service with database name `flight_ci`.

1. Install the pinned Phase 2–4 dependencies.
2. Lint new Phase 4 code with Ruff and execute all Python tests.
3. Create Phase 3 warehouse tables and seed ten synthetic flights.
4. Execute the **entire dbt DAG** (`dbt build`), including its data tests.
5. Verify known synthetic KPIs, unknown-dimension handling and rollback of invalid transactions.
6. Execute source-to-mart gates against the synthetic data.

The CI service is not the production database. No raw ZIP, Bronze, or private `.env` is needed, and no secrets are hard-coded in the workflow.

## Run Python checks on Windows

From `D:\Flight_Operations_Intelligence` with the project's virtual environment installed:

```powershell
.\.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider
.\.venv\Scripts\ruff.exe check --select E4,E7,E9,F,I src/phase4 tests/test_phase4_quality_gates.py tests/test_phase4_ci_workflow.py
```

## Reproduce the isolated PostgreSQL fixture

Docker Desktop must be running. Pick an unused local port such as **5544**; this is deliberately separate from the normal warehouse. The following name and database are reserved for the **throwaway** fixture:

```powershell
docker run --rm -d --name foi-phase4-ci-local -e POSTGRES_DB=flight_ci -e POSTGRES_USER=flight_ci -e POSTGRES_PASSWORD=ci_fixture_only -p 127.0.0.1:5544:5432 postgres:17
$env:POSTGRES_HOST='127.0.0.1'
$env:POSTGRES_PORT='5544'
$env:POSTGRES_DB='flight_ci'
$env:POSTGRES_USER='flight_ci'
$env:POSTGRES_PASSWORD='ci_fixture_only'
$env:FLIGHT_CI_FIXTURE='1'
.\.venv\Scripts\python.exe -m src.phase4.ci_fixture setup
.\.venv\Scripts\dbt.exe build --project-dir dbt --profiles-dir dbt --threads 2
.\.venv\Scripts\python.exe -m src.phase4.ci_fixture verify
.\.venv\Scripts\python.exe -m src.phase4.quality_gates --mode fixture
```

The fixture tool deliberately requires **both** `FLIGHT_CI_FIXTURE=1` and `POSTGRES_DB=flight_ci` before it creates schemas, inserts rows or tests rollback. Do not run these commands against your production warehouse.

After confirming that `foi-phase4-ci-local` is the intended **test-only** container, stop it with `docker stop foi-phase4-ci-local`. Its `--rm` flag means PostgreSQL test rows are discarded; they can be regenerated by the seed command. The main project's PostgreSQL container/volume must remain untouched.

## Check the real two-year warehouse

First start the existing Phase 3 PostgreSQL service and load the normal `.env` settings. Do **not** leave the above fixture environment variables set: start a new terminal for this command.

```powershell
.\.venv\Scripts\python.exe -m src.phase4.quality_gates --mode full --report docs/phase4/quality_report.json
```

`PASS` indicates reconciled data. `REVIEW` is a specifically documented BTS source exception; it needs attention but does not halt the command. `FAIL` indicates a broken invariant and returns a failing exit code. Investigate Silver loading, source manifests, dbt models and the relevant month before publishing refreshed BI results.

To retry CI failures: check the **first** failed Python/dbt node or gate, reproduce on `flight_ci`, fix the root cause, re-run all checks, then re-run the workflow. Do not delete or reset the real warehouse to make a synthetic CI failure disappear.
